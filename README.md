## Введение
**Предметная область:** Кулинарный новостной портал.
Проект представляет собой распределённую информационную систему, обеспечивающую публикацию кулинарного контента, персонализированный подбор рекомендаций и оперативное информирование пользователей.

## Сценарии использования приложения
**Бизнес-цель:** Увеличить вовлеченность и удержание пользователей за счет персонализации кулинарного контента и оперативного информирования аудитории о новых тематических подборках рецептов.

**Функциональность приложения:**
Для достижения бизнес-цели приложение реализует следующий функционал:
* Регистрация, авторизация и аутентификация пользователей (JWT-аутентификация).
* Создание, чтение, редактирование и удаление кулинарных рецептов и новостных статей.
* Добавление рецептов в список "Избранное".
* Получение персональных рекомендаций на основе истории сохраненных рецептов пользователя (через gRPC-сервис).
* Рассылка и получение push-уведомлений в реальном времени при публикации новых тематических подборок.

**Роли пользователей:**
1. **Читатель (User):** имеет право просматривать рецепты, добавлять их в избранное, получать рекомендации и уведомления.
2. **Администратор (Admin):** имеет полный доступ к созданию, просмотру, редактированию и удалению рецептов и тегов, а также управляет рассылками.

**Конкретные сценарии использования:**
1. *Сценарий 1: Чтение и сохранение рецепта (Читатель).* Пользователь авторизуется в системе, открывает главную страницу, переходит в каталог рецептов, открывает карточку рецепта и нажимает кнопку "Добавить в избранное".
2. *Сценарий 2: Создание статьи (Администратор).* Администратор переходит в панель управления, отправляет POST-запрос с данными нового рецепта (название, текст, ингредиенты, теги). Система сохраняет данные в БД.
3. *Сценарий 3: Рекомендация контента (Система/Читатель).* При переходе читателя в личный кабинет, API Service запрашивает у gRPC-сервиса список ID рекомендованных рецептов на основе сохраненных ранее статей пользователя. Читатель видит блок "Вам может понравиться".
4. *Сценарий 4: Уведомление о выходе подборки (Система/Читатель).* Администратор публикует новую кулинарную подборку. API Service отправляет событие в RabbitMQ. Сервис уведомлений (Notification Service) забирает событие и через WebSocket рассылает уведомление всем читателям, находящимся в онлайне.

## Архитектура приложения
Архитектурные решения основаны на микросервисном подходе и использовании современных сетевых протоколов.

**Стек технологий и обоснование их использования:**
* **PostgreSQL:** Реляционная БД, обеспечивающая строгую целостность данных и поддержку сложных связей между сущностями.
* **SQLAlchemy & Pydantic:** ORM-библиотека для безопасного взаимодействия с БД на уровне объектов Python и инструмент для строгой валидации входящих данных.
* **FastAPI (API Service):** Высокопроизводительный асинхронный веб-фреймворк, идеально подходящий для маршрутизации REST API запросов.
* **gRPC (gRPC Service):** Выполняет вычислительную задачу по подбору рекомендаций. Взаимодействует с API Service по RPC (Protocol Buffers), так как этот протокол обеспечивает быстрый межсервисный обмен данными.
* **RabbitMQ:** Надежный асинхронный брокер сообщений. Обеспечивает отказоустойчивую передачу событий от основного API к сервису уведомлений, снимая нагрузку с основного потока.
* **WebSocket (Socket Service):** Технология двунаправленного обмена, необходимая для мгновенной доставки push-уведомлений подключенным клиентам.
* **Docker & Docker Compose:** Применяются для изоляции, контейнеризации всех узлов распределенной системы и обеспечения идентичности среды разработки и продакшена.

## Структура базы данных
Для реализации функционала спроектированы 3 основные сущности (`User`, `Recipe`, `Tag`) и 2 связи типа "многие-ко-многим", обеспечивающие чтение, запись и редактирование данных в соответствии с требованиями предметной области.

**Логическая схема:**
* **Сущность User (Пользователь):** Хранит учетные данные. Выступает в системе в трех ролях:
    * *Как создатель:* связан с публикациями прямой связью "Один-ко-многим" (один пользователь пишет много постов).
    * *Как читатель:* связан с публикациями связью "Многие-ко-многим" через список сохраненного (промежуточная таблица `favorites`) и связан с уведомлениями прямой связью "Один-ко-многим" (один читатель получает множество персональных уведомлений).
* **Сущность Post (Публикация):** Хранит контент, статус публикации (`is_published`) и тип поста (`post_type`).
    * Связана с тегами для категоризации (связь "Многие-ко-многим", промежуточная таблица `post_tags`).
    * Является источником события для рассылки (связь "Один-ко-многим" с таблицей `notifications`).
* **Сущность Tag (Тег):** Используется для фильтрации и поиска кулинарного контента.

## Контейнеризация приложения 

**Цель:** Обеспечение изолированного запуска компонентов распределенной системы, настройка сетевого взаимодействия между сервисами и автоматизация развертывания приложения с использованием Docker и Docker Compose.

### Компоненты приложения

Каждый компонент приложения запускается в отдельном Docker-контейнере.

| Сервис | Назначение | Порт |
|---|---|---|
| db | Хранение данных в PostgreSQL 17 | 5432 |
| api-service | Обработка REST API запросов | 8000 |
| grpc-service | Подбор похожих публикаций | 50051 |
| rabbitmq | Асинхронная передача событий | 5672, 15672 |
| notification-service | Рассылка WebSocket-уведомлений | 8001 |

### Конфигурационные файлы

* `Dockerfile.api` — инструкции для сборки образа API Service.
* `Dockerfile.grpc` — инструкции для сборки образа gRPC Service.
* `Dockerfile.notification` — инструкции для сборки образа Notification Service.
* `docker-compose.yml` — конфигурация сервисов, сети, тома и зависимостей между контейнерами.
* `requirements.txt` — список зависимостей Python.
* `.dockerignore` — исключение ненужных файлов из контекста сборки Docker-образов.
* `.env` — переменные окружения для настройки подключения к сервисам. Файл исключен из системы контроля версий.

### Сетевое взаимодействие

Все контейнеры объединены в общую сеть `app-network` с драйвером `bridge`.

Взаимодействие между контейнерами осуществляется по именам сервисов с использованием встроенного механизма DNS Docker.

* API Service взаимодействует с PostgreSQL для чтения и записи данных.
* API Service обращается к gRPC Service для получения списка похожих публикаций на основе общих тегов.
* API Service отправляет события о создании публикаций в RabbitMQ.
* Notification Service получает события из RabbitMQ и рассылает уведомления подключенным WebSocket-клиентам.
* gRPC Service взаимодействует с PostgreSQL для поиска похожих публикаций.

Параметры подключения к сервисам передаются через переменные окружения.

### Постоянное хранение данных

Для хранения данных PostgreSQL используется именованный том `postgres_data`, подключенный к директории `/var/lib/postgresql/data` внутри контейнера.

Использование тома обеспечивает сохранение данных при остановке, удалении и повторном создании контейнеров.

### Запуск приложения

**Необходимое программное обеспечение:**

* Docker Desktop.
* Docker Compose.

Перед первым запуском необходимо создать файл `.env` на основе
шаблона `.env.example`.

Для Windows (PowerShell):

```powershell
Copy-Item .env.example .env
```

Для Linux и macOS:

```bash
cp .env.example .env
```

После создания файла `.env` необходимо заменить демонстрационные
пароли собственными.

Файл `.env` содержит конфиденциальные данные и не добавляется
в систему контроля версий.

Сборка образов и запуск всех сервисов:

```bash
docker compose up -d --build
```

Проверка состояния контейнеров:

```bash
docker compose ps
```

Заполнение базы данных тестовыми данными (при необходимости):

```bash
docker compose exec api-service python seed.py
```

После запуска доступны следующие ресурсы:

* REST API: http://localhost:8000
* Swagger UI: http://localhost:8000/docs
* Панель управления RabbitMQ: http://localhost:15672
* Notification Service: localhost:8001

Остановка и удаление контейнеров с сохранением данных:

```bash
docker compose down
```

Повторный запуск приложения:

```bash
docker compose up -d
```
